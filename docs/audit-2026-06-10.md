## 1. Critical / High — fix first

### C1. debugtui panics on tavern tier 7 (anomaly tier)
`internal/debugtui/render.go:113`
```go
stars := strings.Repeat("★", tier) + strings.Repeat("☆", 6-tier)
```
`strings.Repeat` panics on negative count. Tier 7 is real (the live TUI guards it:
`tui/tui.go:1319` uses `max(0, 6-tier)` and has a `case 7` color). Replaying any game
that reached tier 7 crashes the replay TUI on first header render.

### H1. Duos: partner combat copies corrupt the local board snapshot
`internal/gamestate/processor_visitor.go:584-597`, `processor.go:427-457`,
`state.go:332-368` (`UpdateSnapshotFromCombatCopy`).
Combat-copy peak tracking registers any SETASIDE minion with
`ControllerID == localPlayerID` during combat — but in duos the **partner's** combat
copies also carry `CONTROLLER=localPlayerID` (the code's own comment at
`processor.go:826-828` says so). `UpdateSnapshotFromCombatCopy` then matches local
snapshot slots **by CardID**, so a partner minion sharing a CardID with a local one
(common in shared-tribe duos comps) raises the local snapshot's stats to the partner's
values, corrupting the final restored board. The partner-board path has a
`partnerCombatActive` cutoff; this path has no partner exclusion at all.

### H2. Update check breaks permanently at v0.10.0 (lexicographic version compare)
`internal/update/update.go:106-113`
```go
return latest != current && latest > current
```
String comparison: `"0.10.0" > "0.9.0"` is **false** in Go. The moment v0.10.0 ships,
every v0.9.x user stops getting update notifications. Also `"0.6.1-beta" > "0.6.1"` is
true, so stable users get "updated" to older betas. Tests only cover same-width versions.
Fix: proper semver compare (`golang.org/x/mod/semver` is already in the dep graph).

### H3. `safe-test.sh` isolation is a false promise — env vars consumed by nothing
`scripts/safe-test.sh:40-41` exports `BS_CONFIG_DIR` / `BS_DATA_DIR`; **zero Go code
reads them** (verified by grep). `config.Load()` resolves from `os.UserHomeDir()`, and
`HOME` is not overridden by the script. Any daemon/integration run under the wrapper
still reads and writes the real `~/.battlestream/` — exactly what CLAUDE.md claims it
prevents. Fix: either consume the env vars in `internal/config`, or have the script
override `HOME`.

### H4. `Watcher.Stop()` never closes `Lines` — capture pipeline leaks and drops final flush
`internal/watcher/watcher.go:264-271` — doc comment says "closes the Lines channel";
nothing ever closes it. `internal/capture/pipeline.go:46-50` does
`for line := range w.Lines { ... }; p.Flush()` — after `Close()` that goroutine blocks
forever and `Flush()` (final buffered line) never runs.

### H5. TUI reconnect storm: leaked gRPC clients and duplicated poll chains
`internal/tui/tui.go:330-344, 1417-1448`
Multiple in-flight commands can each emit `disconnectedMsg`; the handler doesn't check
whether a reconnect is already pending, so each schedules another `connectCmd`. Each
`connectedMsg` overwrites `m.client` **without closing the previous connection** and
starts fresh `aggTickCmd`/`gameTickCmd` chains; old chains keep re-arming. Long-running
TUIs against a flaky daemon accumulate connections and parallel pollers.

### H6. bscapture mid-game catchup attaches live screenshots to historical games
`internal/capture/loop.go:62-160`, `pipeline.go:28-31`
The pipeline replays the whole Power.log (`ReadFromStart: true`) while a 1s ticker
polls tracker state. A tick landing mid-replay inside an *earlier completed game* sees
`InGame()==true` with that old game's ID, calls `InitGame(oldID)`, and screenshots the
current desktop into that historical game. Worse: `store.go:86-96` overwrites the JPEG
on disk **before** the `UNIQUE(game_id, sequence)` insert fails — silently corrupting
prior capture data. Separately, when GameID never populates, `loop.go:110` `continue`s
with no log line — the game is silently never captured (this is the "empty GameID
mid-game join" issue from project memory, precisely characterized). Fix: don't start
capturing until the replay has caught up to the tail (e.g. a catch-up barrier from the
watcher, or compare event timestamps to wall clock).

### H7. debugtui memory blowup: full deep-copied state snapshot per event
`internal/debugtui/replay.go:84-117, 139`
Every event appends a `Step` holding a full deep copy of `BGGameState` (board,
enchantments, modifications, partner board) plus all raw log lines retained as strings.
Memory is O(events × state-size), super-linear late game; the combined TUI's log
fallback loads **all** discovered log files. Hundreds of MB to GB is realistic on a
92K-line log. Related: `tui/combined.go:223-231` installs an empty model after a 5s
init timeout and throws away the real result — large DBs easily exceed 5s, so the user
permanently sees an empty replay tab.

### H8. gRPC `ListGames` returns page size as `Total`
`internal/api/grpc/server.go:139-146` — `Total: int32(len(metas))` is computed *after*
limit/offset. Any client paginating off `Total` stops after the first page. The REST
handler does it correctly (`rest/server.go:175-176`); also note gRPC doesn't filter
placement-0 stale games while REST does — the two APIs return different lists.

### H9. debugtui nil-pointer panic on source switch in combined TUI
`internal/debugtui/model.go:737-740` — `m.progress` is only set in `New()`;
`NewFromReplay()` (the combined-TUI DB path) leaves it nil. Pressing `L` sets
`m.loading = true` and the next `View()` dereferences nil → the whole TUI dies.

## 2. Medium — real bugs, lower blast radius

### Gamestate / parser

- **M1. Staleness clock misses dispatcher-routed events.** `processor.go:214` —
  `lastEventTime` is only updated in `Handle()`; events routed through the visitor
  dispatcher don't refresh it. Works today only because high-frequency events are
  unmigrated; completing the visitor migration will make `CheckStaleness` kill every
  live game at 3 minutes. Move the timestamp update to the daemon loop or dispatcher.
- **M2. Builder phase gates silently fall through to ungated `Handle()` paths.**
  `builder/builder.go:217-368` + `cmd/battlestream/main.go:285` — when the builder
  declines to build (phase gate), the daemon routes the raw event to `proc.Handle(e)`,
  which has **no equivalent guard** (e.g. `BACON_FREE_REFRESH_COUNT` during combat is
  fully processed). The dispatcher's "phase confusion is structurally impossible" claim
  is false for everything the builder declines.
- **M3. Bonus Gold counter can never return to 0.** `processor.go:1869-1883` — the
  early return on `sure == 0 && overconfidenceCount == 0` also prevents *clearing* an
  existing counter; once set, it displays stale for the rest of the game.
- **M4. Authoritative duos teammate signal dropped if backup detection fired first.**
  `processor_visitor.go:657-658` — `if ... || p.isDuos { return nil }` discards
  `BACON_DUO_TEAMMATE_PLAYER_ID` when duos was already set via the backup path, so
  `duosFromTeammate` never gets set and a later `PUNISH_LEAVERS=0` incorrectly clears
  duos despite authoritative evidence.
- **M5. `UpsertMinion` wholesale-replaces board entries, wiping per-minion
  `Enchantments`.** `state.go:408-421` + both upsert callers — re-registration events
  (golden upgrades, zone re-asserts) construct a fresh `MinionState` without
  enchantments, silently erasing the attached list.

### Store / persistence

- **M6. Game-list integrity is fragile.** Three compounding issues in
  `internal/store/store.go`:
  - `SaveGame` (74-84) treats *any* `txn.Get` error as "list doesn't exist" and
    overwrites the list with one element — a transient read error orphans all history.
  - `SaveFullGame` (182-205) uses two separate transactions; a crash between them
    leaves a listed game with no state. Trivially fits one transaction.
  - `HasGame` (168-174) returns false on DB error, and the list append is
    unconditional — dedup is a non-atomic check-then-act in `main.go:291`; a duplicate
    list entry double-counts in aggregates forever. Also `HasGame("")` is false, so
    empty-GameID games write under the bare key `game:meta:`.
- **M7. fileout "atomic" write isn't crash-durable.** `fileout/writer.go:167-186` —
  no `fsync` before rename; power loss can leave a truncated `game_state.json`. Also
  stale `current/partner_stats.json` survives into subsequent solo games (128-144).

### Config

- **M8. `BS_` env overrides only work for the 4 keys with defaults.**
  `config/config.go:153-157` — viper's `AutomaticEnv`+`Unmarshal` limitation; profile
  keys and `BS_ACTIVE_PROFILE` are silently ignored. Same issue likely affects
  bscapture's `BSC_POWER_LOG_PATH`.
- **M9. `~` not expanded for `hearthstone.log_path`/`install_path`.**
  `config/config.go:250-253` — `expandPaths` covers only DB and output paths; a
  `log_path: ~/...` makes the daemon silently tail nothing.
- **M10. `SaveTUI` ignores `--config` and rewrites non-atomically.**
  `config/config.go:266-282` — hardcodes `~/.battlestream/config.yaml`, discards read
  errors (can create a half-empty config), races the atomic `Save()` writer. Also
  invoked as fire-and-forget `go m.cfg.SaveTUI()` per divider drag (`tui.go:1136`) —
  concurrent unsynchronized writes to the same file.

### Daemon / API

- **M11. Store closed while servers may still serve.** `main.go:404-424` — gRPC
  `GracefulStop` and REST `Shutdown` run in unawaited goroutines; in-flight requests
  can hit BadgerDB after `store.Close()`. Also `GracefulStop` never completes while a
  TUI event stream is attached. And `fmt.Scanln()` at 411-419 parks the main goroutine
  so SIGINT doesn't exit cleanly while the log.config prompt is up.
- **M12. WS/SSE firehose readable by any website.** `rest/server.go:23-25, 357` —
  `CheckOrigin` always true, SSE sets `Access-Control-Allow-Origin: *`, API key empty
  by default. Any web page in the user's browser can stream the event feed from
  `127.0.0.1:8080`. Privacy-level impact; add an origin check (localhost origins only)
  as a cheap fix.
- **M13. `/v1/player/{name}` ignores the name** — every name returns identical global
  stats (`rest/server.go:289-334`, same in gRPC). Acknowledged in a comment but ships
  as a lying endpoint.

### TUI (combined mode)

- **M14. Each Tab toggle back to live adds another event-stream reader.**
  `combined.go:179-187` — N round-trips → N+1 concurrent readers, each daemon event
  triggers N+1 full-state RPCs.
- **M15. Keys/mouse leak into the hidden live model during replay mode.**
  `combined.go:108-124, 155-166` — `o` opens a browser, drags hit the invisible live
  divider and trigger config writes. Plus replay-tab mouse coordinates are off by one
  row (no `parentYOffset` equivalent).
- **M16. Replay load error + any key quits the whole program.** `model.go:370-372` —
  `tea.Quit` from the replay tab kills the working live dashboard.

### Watcher

- **M17. Session-dir switch failure modes.** `watcher.go:170-214` — old tails stopped
  before new ones start; on failure the watcher has zero tails forever (latent —
  shipping config uses `MustExist: false`). `tail.Cleanup()` never called → slow
  inotify leak per HS restart. `ResolvedDir` goes stale after a switch.
